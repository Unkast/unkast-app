## 2. Comportement à la suppression (45 clés étrangères, catalogue `pg_constraint.confdeltype`)

## 3. Constats importants

### I1. `project_credits` n'a aucune contrainte d'unicité

- Preuve : base de production, catalogue `pg_constraint` : seules `project_credits_pkey` et `credit_has_person` existent. Définition : `supabase/schema.sql:45-52`.
- Chemins qui peuvent créer un doublon :
  - `src/app/api/credits/[id]/route.ts:43-63` : le statut de la demande est lu, puis le crédit est inséré, puis le statut est mis à jour (ligne 72). Deux appels simultanés passent tous les deux le contrôle de la ligne 43 et insèrent deux crédits. La route voisine a fermé cette course par une mise à jour conditionnelle (`src/app/api/invitations/project/[id]/route.ts:43-48`), pas celle-ci.
  - `src/app/api/invitations/project/[id]/route.ts:59-63` : l'acceptation d'une invitation insère un crédit sans regarder si la personne est déjà créditée avec le même rôle (par une demande de crédit, ou comme Responsable à la publication).
  - `src/app/api/invitations/route.ts:62-68` : crédit fantôme créé à chaque invitation email, sans contrôle sur le nom.
- État actuel : 0 groupe en double sur (film, profil, rôle normalisé), sur 36 crédits (`count(*)` en base). La contrainte peut donc être posée sans nettoyage préalable.
- Risque : la même personne affichée deux fois sur un film, compteurs et « films liés » faussés (`related_public_projects` compte les collaborateurs communs).
- Correction proposée : index unique partiel sur `(project_id, profile_id, lower(btrim(role_on_project))) WHERE profile_id IS NOT NULL` (plusieurs rôles par personne restent permis). Traiter le code `23505` comme « déjà crédité » dans les trois routes. Rendre la décision de `credits/[id]` atomique (mise à jour `WHERE status = 'pending'` avant l'insertion, comme pour les invitations).

### I2. Un jeton push n'est pas unique : le même appareil peut rester lié à deux comptes

- Preuve : base de production, catalogue `pg_constraint` : `push_tokens_profile_id_token_key UNIQUE (profile_id, token)`, rien sur `token` seul. Table absente du dépôt.
- Code : `src/app/api/notifications/register/route.ts:27-34` fait un upsert sur `profile_id,token`. Le retrait à la déconnexion (`:47-55`) exige une session valide (`:49-50`) : si la session a expiré ou si l'appel échoue, le jeton reste attaché à l'ancien compte.
- Risque : sur un appareil où une autre personne se connecte ensuite, les notifications de l'ancien compte continuent d'arriver, avec le nom de l'expéditeur et les 80 premiers caractères du message (`src/app/api/messages/route.ts:247-251`).
- Correction proposée : unicité sur `token` seul, et à l'enregistrement, réattribuer le jeton au compte courant (upsert sur `token`, écrit par le service role puisque la RLS ne laisse voir que ses propres jetons).

### I3. Supprimer un compte admin efface son journal d'actions

- Preuve : base de production, catalogue `pg_constraint` : `admin_logs_admin_id_fkey`, `confdeltype = c` (CASCADE), `admin_id NOT NULL`. Table absente du dépôt.
- Contradiction avec le dépôt : `supabase/migrations/20260810_pro_grants.sql:63` affirme que `admin_logs` « reste la source d'audit complète et n'est pas affectée » par la suppression d'un admin. C'est faux en base : les lignes partent en cascade.
- Risque : perte de l'historique de modération (suspensions, refus de films, grants Pro) le jour où le compte admin est supprimé ou recréé. 10 lignes aujourd'hui (`count(*)`). Classé important et non critique parce qu'aucun chemin du code ne supprime un compte.
- Correction proposée : passer la clé en `ON DELETE SET NULL` avec `admin_id` nullable (ou `RESTRICT` si un admin ne doit jamais être supprimé), et garder le nom de l'admin dans `details` au moment de l'écriture.

### I4. Supprimer un profil efface des données qui appartiennent à d'autres, et des pièces de modération

- Preuves (base de production, catalogue `pg_constraint`) :
  - `conversations_participant_1_fkey` et `conversations_participant_2_fkey` en CASCADE, puis `messages_conversation_id_fkey` en CASCADE : l'autre personne perd toute la conversation, y compris ses propres messages.
  - `reports_reporter_id_fkey` en CASCADE alors que la colonne est nullable depuis `supabase/migrations/20261008_film_management.sql:1357` (NULL = signalement système) : les signalements en attente déposés par la personne disparaissent.
  - `project_claims_claimant_id_fkey` en CASCADE (`20261008_film_management.sql:277`) : une revendication en cours disparaît avec son auteur, le justificatif reste dans le bucket `claims` sans ligne pour le retrouver.
  - `reports.target_id` n'a pas de clé (cible polymorphe) : un signalement qui vise un message ou un profil supprimé reste en file, sans cible. Le code le tolère (`src/app/api/admin/route.ts:97` utilise `maybeSingle`), l'admin voit alors un signalement vide.
- Risque : un compte signalé pour ses messages qui est supprimé emporte les messages, donc la preuve. Le quota gratuit « 2 personnes contactées » (`docs/database.md:160`) se libère aussi, puisqu'il compte les conversations.
- Correction proposée (décision produit à valider) : `reports.reporter_id` en SET NULL ; pour les conversations, soit participants nullables en SET NULL avec un affichage « compte supprimé », soit une suppression logique du profil au lieu d'un DELETE ; purge des signalements dont la cible n'existe plus au moment de la suppression.

### I5. L'unicité sur les demandes de crédit bloque toute nouvelle demande après une décision

- Preuve : base de production, catalogue `pg_constraint` : `credit_requests_project_id_requester_id_key UNIQUE (project_id, requester_id)`, sans condition sur le statut. Table absente du dépôt.
- Code : `src/app/api/credits/request/route.ts:47-58` insère une ligne et traduit `23505` par « Tu as déjà une demande en cours ». La ligne refusée ou acceptée n'est jamais supprimée : le demandeur ne peut retirer qu'une demande en attente (`src/app/api/credits/[id]/route.ts:114-120`, policy décrite dans `docs/database.md:343-344`).
- Risque : une personne refusée une fois, ou créditée puis retirée (`src/app/api/dashboard/credits/route.ts:112-117`), ne peut plus jamais redemander un crédit sur ce film, avec un message qui dit le contraire de la réalité. Même forme sur `project_invitations_project_id_invited_profile_id_key` (`src/app/api/invitations/project/route.ts:56-59`), atténuée parce que l'inviteur peut supprimer l'ancienne invitation (`src/app/api/invitations/project/[id]/route.ts:105`) ; une seule invitation par personne et par film, donc un seul rôle.
- Correction proposée : unicité partielle `WHERE status = 'pending'`, sur le modèle de `project_claims_one_pending` (`20261008_film_management.sql:286`), ou réouverture de la ligne existante par la route.

### I6. Liste des conversations : 3 requêtes par conversation, sans limite

- Preuve : `src/app/api/messages/route.ts:264-287`. Une requête pour la liste (`:264-267`, sans `limit`), puis pour chaque conversation trois requêtes exécutées l'une après l'autre : profil de l'autre (`:271`), dernier message (`:272-273`), compteur de non lus (`:274-276`).
- Chiffre : 1 + 3 N requêtes. 4 conversations aujourd'hui en base, soit 13 requêtes au maximum par appel ; 50 conversations = 151 requêtes pour un Pro, à chaque ouverture de la messagerie.
- Risque : temps de réponse proportionnel au nombre de conversations, sur la route la plus consultée par un compte actif.
- Correction proposée : une requête pour les profils (`.in("id", ...)`), et une fonction SQL ou une vue qui renvoie par conversation le dernier message et le nombre de non lus (les index `idx_messages_conversation` et `idx_messages_unread` existent déjà) ; ajouter une limite ou une pagination.

### I7. `/api/dashboard/credits` : une requête par ligne, trois fois

- Preuve : `src/app/api/dashboard/credits/route.ts:31-43` (un profil par demande reçue), `:51-64` (un film par crédit), `:73-86` (un film par demande envoyée). Aucune des trois listes n'a de limite (`:24-28`, `:46-49`, `:67-71`).
- Chiffre : 3 + R + C + D requêtes (R demandes reçues, C crédits, D demandes envoyées). Une personne créditée sur 20 films avec 5 demandes reçues : 28 requêtes.
- Correction proposée : jointures intégrées (`project_credits` avec `projects(title, slug)`, `credit_requests` avec `projects(title, slug)`), et un seul `.in("id", ...)` pour les noms des demandeurs. 3 ou 4 requêtes au total.

### I8. Le dépôt ne permet pas de reconstruire la base, et les types décrivent des statuts que la base refuse

- Objets présents en base et absents de tout fichier SQL du dépôt (recherche par nom dans `supabase/schema.sql` et `supabase/migrations/`) :
  - 9 tables sans `CREATE TABLE` : `conversations`, `messages`, `credit_requests`, `project_invitations`, `invitations`, `reports`, `admin_logs`, `push_tokens`, `waitlist`, avec leurs clés, leurs index (`idx_admin_logs_*`, `idx_conversations_*`, `idx_messages_*`, `idx_reports_*`, `idx_waitlist_type`, `idx_push_tokens_profile`, `idx_invitations_*`) et leurs contraintes d'unicité.
  - Environ 35 colonnes de `profiles` et 3 de `projects` (`status`, `poster_url`, `preview_url`) : `schema.sql:11-22` et `:32-42` s'arrêtent à 10 et 9 colonnes.
  - 13 CHECK : `credit_requests_status_check`, `project_invitations_status_check`, `reports_status_check`, `waitlist_status_check`, `waitlist_type_check`, `projects_status_check`, `profiles_plan_check`, `profiles_recruiter_status_check`, `profiles_display_name_preference_check`, les trois `profiles_show_*_to_check`, et la version d'origine de `profiles_account_type_check` (seule sa réécriture est versionnée, `20261017_admin_account.sql:32-33`).
  - Valeurs `moyen-metrage` et `long-metrage` de l'enum `project_category` (`schema.sql:6` n'en liste que 6, la base en a 8).
  - Fonction `rls_auto_enable()` et déclencheur d'événement `ensure_rls` (catalogue `pg_event_trigger`).
  - `schema.sql:34` déclare encore `projects.profile_id ... ON DELETE CASCADE NOT NULL`, la base est en SET NULL nullable.
- Statuts faux dans les types et la doc, alors que la base les contraint :
  - `src/types/database.ts:89-90` : `CreditRequestStatus` et `InvitationStatus` valent `'pending' | 'accepted' | 'declined'`. La base n'accepte que `pending`, `accepted`, `refused` (CHECK ci-dessus). Les routes écrivent bien `refused` (`src/app/api/credits/[id]/route.ts:26`, `src/app/api/invitations/project/[id]/route.ts:26`).

- Risque : impossible de monter une base de test ou de reprise fidèle depuis le dépôt ; un développement qui suit les types écrit `declined` ou `invited` et reçoit une erreur `23514` en production.
- Correction proposée : exporter le schéma réel (`pg_dump --schema-only` du schéma `public`) dans une migration de référence qui remplace `schema.sql`, puis corriger les trois types et le tableau des statuts de `docs/database.md`.
