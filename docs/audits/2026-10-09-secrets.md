# Audit des secrets exposés

Date : 09/10/2026
Périmètre : dépôt `unkast` (branche `main`, 83 commits, tout l'historique local), dossier `.next` du serveur de dev, fichier `.env.local` (comparaison locale, aucune valeur affichée), une requête en lecture seule sur la base de production.
Mode : lecture seule. Aucune correction appliquée.

## Contexte à connaître

Le dépôt GitHub `Unkast/unkast-app` est **public** (`gh repo view`, visibilité `PUBLIC`). Tout ce qui est versionné, y compris l'historique, les migrations, la documentation et le fichier seed, est lisible par n'importe qui. Les constats ci-dessous sont classés en tenant compte de ce fait.

## Résultat principal

Aucune clé secrète réelle n'a été trouvée dans le code, dans l'historique git ni dans le bundle envoyé au navigateur. Les valeurs de `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY` et du compte de service Firebase présentes dans `.env.local` ont été recherchées à l'identique dans les fichiers suivis, dans tout l'historique (`git log -S`) et dans `.next` : zéro occurrence.

Le seul vrai problème est un mot de passe public sur des comptes qui existent en production.

---

## Critique

### C1. Six comptes de démonstration en production avec un mot de passe public

- **Où** : `supabase/seed.sql` lignes 9 à 14 (présent depuis le premier commit `fc30500`).
- **Ce qui ne va pas** : le fichier crée six utilisateurs `...@demo.com` avec le même mot de passe écrit en clair dans l'appel `crypt('...')`. Ce fichier a été exécuté sur la base de production : une requête en lecture seule du 09/10/2026 trouve 6 comptes `@demo.com`, et pour les 6 le mot de passe du seed est toujours valide. Le dépôt étant public, ce mot de passe l'est aussi.
- **État constaté** : aucun de ces comptes ne s'est jamais connecté (`last_sign_in_at` vide pour les 6), aucun n'est admin, un a le plan Pro.
- **Risque concret** : n'importe qui peut se connecter sur `app.unkast.com` avec l'un de ces comptes. Il peut alors publier ou modifier des films sous une fausse identité, créditer des membres, et, avec le compte Pro, écrire directement aux membres par la messagerie. Les emails et le mot de passe se lisent dans le dépôt en quelques secondes.
- **Correction proposée** :
  1. Tout de suite, en base : remplacer le mot de passe de ces six comptes par une valeur aléatoire non conservée, ou les bannir côté Auth (`banned_until`), ou les supprimer si les profils de démonstration ne servent plus.
  2. Vérifier dans les journaux Auth de Supabase qu'aucune connexion `@demo.com` n'a eu lieu.
  3. Dans le dépôt : retirer le mot de passe du seed (le générer à l'exécution) et noter dans le fichier qu'il ne doit jamais être exécuté en production. Le retirer de l'historique n'apporte rien une fois le mot de passe changé en base.

## Important

### I1. Le poste de développement travaille sur la production avec la clé qui contourne la RLS

- **Où** : `.env.local` (non versionné), variables `NEXT_PUBLIC_SUPABASE_URL` et `SUPABASE_SERVICE_ROLE_KEY`. Le compte Supabase ne contient qu'un seul projet (`unkast-app`), et les deux clés locales portent la même référence de projet.
- **Ce qui ne va pas** : il n'y a pas de base de développement. Le serveur local (`localhost:3000`) lit et écrit en production avec la clé service role, qui ignore toutes les policies.
- **Risque concret** : un bug local, un script de test ou une route en cours d'écriture modifie ou supprime des données réelles. La clé la plus sensible du projet vit en clair sur un poste de travail, et tout outil qui lit ce dossier y a accès.
- **Correction proposée** : créer un second projet Supabase (ou une branche Supabase) pour le développement et y faire pointer `.env.local`. Garder la clé service role de production uniquement dans Vercel.

## Mineur

### M1. Clé d'API Firebase Android dans un dépôt public

- **Où** : `android/app/google-services.json` ligne 18 (versionné depuis le commit `39381d4` du 10/06/2026).
- **Ce qui ne va pas** : ce n'est pas un secret au sens strict, cette clé est faite pour être embarquée dans l'APK. Mais elle est ici lisible sans même décompiler l'application.
- **Risque concret** : si la clé n'est pas restreinte dans Google Cloud, quelqu'un peut l'utiliser pour appeler des API Google au nom du projet et consommer son quota.
- **Correction proposée** : dans la console Google Cloud, vérifier que la clé est restreinte à l'application Android (nom de paquet et empreinte SHA-1) et aux seules API utilisées. Aucune rotation nécessaire si c'est le cas.

### M2. Messages d'erreur bruts de la base renvoyés au navigateur

- **Où** : 30 occurrences dans `src/app/api`, par exemple `src/app/api/availability/route.ts` lignes 67, 115, 147 et 176, `src/app/api/avatar/route.ts` ligne 57, `src/app/api/dashboard/profile/route.ts` ligne 315, `src/app/api/dashboard/career/route.ts` lignes 74, 97 et 178.
- **Ce qui ne va pas** : la réponse contient `error.message` tel que renvoyé par PostgREST ou le stockage.
- **Risque concret** : pas de fuite de secret, mais ces messages révèlent des noms de tables, de colonnes, de contraintes et de policies, utiles à quelqu'un qui cherche une faille.
- **Correction proposée** : journaliser le message complet côté serveur et renvoyer au client un message neutre avec un code.

### M3. Aucune barrière de compilation autour de la clé service role

- **Où** : `src/lib/supabase/admin.ts` ligne 1. Le paquet `server-only` n'est utilisé nulle part dans `src`.
- **Ce qui ne va pas** : la règle « ne jamais importer ce fichier côté client » repose sur un commentaire. Aujourd'hui elle est respectée : aucun fichier `"use client"` n'importe `supabase/admin`, `adminGuard`, `auth-guard`, `stripe`, `email` ni `firebase-admin`.
- **Risque concret** : faible. La variable n'a pas le préfixe `NEXT_PUBLIC_`, donc sa valeur ne partirait pas dans le bundle même en cas d'import par erreur. Mais l'erreur passerait inaperçue jusqu'à l'exécution.
- **Correction proposée** : ajouter `import "server-only"` en tête de `src/lib/supabase/admin.ts`, `src/lib/adminGuard.ts`, `src/lib/auth-guard.ts`, `src/lib/stripe.ts`, `src/lib/email.ts` et `src/lib/firebase-admin.ts`. Le build échouera alors à la première importation côté client.

### M4. `.gitignore` ne couvre pas les fichiers de signature Android

- **Où** : `.gitignore` (section `# android`, fin du fichier).
- **Ce qui ne va pas** : `.env*` et `*.pem` sont couverts, mais pas `*.jks`, `*.keystore` ni `keystore.properties`. Aucun fichier de ce type n'existe aujourd'hui dans `android/`, et `android/app/build.gradle` ne contient aucun mot de passe de signature.
- **Risque concret** : le jour où un keystore de publication est posé dans `android/`, un `git add` l'envoie dans un dépôt public.
- **Correction proposée** : ajouter `*.jks`, `*.keystore` et `keystore.properties` au `.gitignore`.

### M5. Adresse IP et clé dérivée de l'email dans les journaux d'erreur

- **Où** : `src/lib/rate-limit.ts` lignes 45, 48 et 53. Les clés journalisées incluent `signup:${ip}`, `search:${ip}`, `waitlist:${ip}` et `resend-confirm:${emailKey}`.
- **Ce qui ne va pas** : en cas d'erreur du limiteur, la clé complète est écrite dans les journaux Vercel.
- **Risque concret** : donnée personnelle dans des journaux, seulement sur le chemin d'erreur. Aucun secret.
- **Correction proposée** : journaliser le préfixe de la clé (`signup`, `search`) sans la partie identifiante.

## Points vérifiés sans constat

- **Fichiers `.env`** : seul `.env.local.example` est suivi par git. `.env`, `.env.local`, `.env.production` et `.env.development.local` sont ignorés (`git check-ignore`). Aucun fichier `.env` n'a jamais été versionné dans l'historique.
- **`.env.local.example`** : ne contient que des gabarits (`<...>`), aucune valeur réelle. Les 16 variables lues par le code y figurent toutes.
- **Variables `NEXT_PUBLIC_`** : quatre seulement (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SITE_URL`, `BILLING_ENABLED`), aucune secrète. La clé publique locale porte bien le rôle `anon`, la clé service le rôle `service_role`.
- **Historique** : recherche par motifs (jetons JWT, clés Stripe, Resend, Google, Supabase, GitHub, AWS, clés privées, chaînes de connexion Postgres) sur les lignes ajoutées de tous les commits. Un seul résultat, la clé du constat M1.
- **Cron** : `src/app/api/cron/pro-expiry/route.ts` ligne 25 refuse toute requête si `CRON_SECRET` est absent ou différent.
- **Webhook Stripe** : `src/app/api/billing/webhook/route.ts` ligne 43 vérifie la signature sur le corps brut.
- **Réponses d'API** : `/api/me` lit `stripe_customer_id` mais ne renvoie qu'un booléen (`has_stripe_customer`). Aucun jeton ni identifiant Stripe renvoyé au client.
- **Journaux** : un seul `console.log` dans `src`. Aucun secret, en-tête d'autorisation ni cookie journalisé.
- **Documentation et migrations** : aucun motif de secret, aucune URL de projet Supabase, aucune adresse personnelle dans `docs/`, `supabase/` et `src/`.
- **`.claude/settings.json`** (suivi) : aucune clé ni jeton.
